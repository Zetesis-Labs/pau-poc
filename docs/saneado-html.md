# Saneado del HTML de Markdown en la web

## Decisión aplicada

Sanear en `web/src/componentes/Markdown.tsx`, **después** de `renderizar(texto)` y de la función opcional `resaltar`, justo antes de `dangerouslySetInnerHTML`. Se usa DOMPurify 3.4.16 en el navegador con su perfil predeterminado, que admite HTML, SVG y MathML, y se excluyen etiquetas de estilos y formularios. No añadir etiquetas ni atributos a la lista permitida para hacer pasar un caso de KaTeX sin investigar primero su salida concreta. Marked declara expresamente que su HTML no está saneado; DOMPurify advierte que modificar el HTML después de sanearlo puede anular la protección. [Marked](https://marked.js.org/), [DOMPurify](https://github.com/cure53/DOMPurify/blob/main/README.md)

El límite de confianza queda así: `Markdown` es el único componente que convierte el HTML interno en DOM. `web/src/dominio/markdown.ts` puede continuar como conversor puro de Markdown/TeX a una **cadena HTML no saneada**; conviene dejar explícito ese contrato en su nombre o documentación. El comentario de `dangerouslySetInnerHTML` documenta ahora que DOMPurify sanea el resultado final. La llamada opcional a `resaltar` también produce HTML interno no saneado. Ninguno de esos resultados debe insertarse directamente en otro componente.

La comprobación del entorno debe cerrar el paso al HTML si no hay un DOM de navegador compatible o si DOMPurify indica `isSupported === false`: devolver `<div className={className}>{texto}</div>` como texto React (React lo escapa), sin llamar a `dangerouslySetInnerHTML`. No usar el HTML de Marked como fallback. Las rutas que muestran Markdown tienen `ssr: false` (`web/src/routes/index.tsx`; la otra ruta, `catalogo.tsx`, no lo usa), de modo que el componente interactivo se renderiza en cliente; el fallback mantiene seguro un futuro uso durante SSR o prerender. DOMPurify necesita un DOM para ejecutarse en servidor y recomienda `jsdom` actualizado allí, lo cual añade una dependencia de ejecución que aquí no hace falta. Además, en navegadores sin soporte DOMPurify puede devolver la entrada intacta: se debe consultar `isSupported` antes de usar su resultado. [DOMPurify: servidor y compatibilidad](https://github.com/cure53/DOMPurify/blob/main/README.md)

KaTeX se configura hoy con `output: "htmlAndMathml"`; su documentación indica que esa salida incluye MathML para accesibilidad y que el saneado requiere una lista generosa, incluso SVG y MathML. El perfil predeterminado de DOMPurify admite ambos. Evitar `USE_PROFILES: { html: true }`, que excluye MathML y SVG. Mantener `trust` de KaTeX en su valor predeterminado `false`, ya que activarlo permite comandos capaces de cargar recursos o cambiar atributos HTML. [KaTeX: opciones](https://katex.org/docs/options), [KaTeX: seguridad](https://katex.org/docs/security), [DOMPurify: perfiles](https://github.com/cure53/DOMPurify/blob/main/README.md)

## Alternativa descartada por ahora

`sanitize-html` funciona bien para HTML con una lista explícita de elementos y atributos, pero su lista predeterminada no incluye SVG ni MathML. Mantener una lista propia que conserve toda la salida de KaTeX implicaría seguir sus cambios de etiquetas, atributos y mayúsculas sensibles a SVG. La documentación de `sanitize-html` exige ajustes del parser para preservar nombres SVG; también advierte que algunos cambios del parser son delicados para la seguridad. Abrir todos los atributos para salvar la presentación sería un bypass de la política. Para este uso en navegador, DOMPurify evita esa configuración extensa. [sanitize-html: README](https://github.com/apostrophecms/apostrophe/blob/main/packages/sanitize-html/README.md)

## Comprobaciones de regresión

- Verificar con pruebas de componente en DOM que `<script>`, manejadores como `onerror`/`onload` y enlaces `javascript:` no sobreviven a la ruta completa `renderizar → resaltar → sanear → insertar`.
- Verificar que fórmulas inline y de bloque, `\ce{…}`, tablas, enlaces ordinarios, `<mark>` y la salida HTML/MathML de KaTeX siguen visibles. Probar SVG legítimo de KaTeX si aparece en la salida real.
- Probar el fallback sin `window` o con `isSupported === false`: debe mostrar el Markdown como texto, sin `dangerouslySetInnerHTML`.
- Mantener como último paso el saneado. Si luego se añade otra transformación de HTML, mover el saneado detrás de ella.

DOMPurify centra su garantía en impedir ejecución de JavaScript; su configuración predeterminada conserva CSS en `<style>` y en atributos `style`, y no impide todas las solicitudes a recursos externos. Si el contenido publicado se considera adversarial también frente a CSS o seguimiento, habrá que restringir esos elementos o establecer una política de contenido adicional, comprobando primero la compatibilidad con KaTeX. Esa cuestión es separada del cierre del XSS en el punto de inserción. [DOMPurify: objetivos y límites de seguridad](https://github.com/cure53/DOMPurify/wiki/Security-Goals-&-Threat-Model)
